# Feature Specification: CI/CDワークフロー

**Feature Branch**: `007-ci-workflow`  
**Created**: 2026-04-24  
**Status**: Draft  
**Input**: User description: "GitHubのmainブランチへのPush/Pull Request作成時にテスト/ビルドを実行するGitHub Actionsワークフロー"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Pull Request時の自動品質チェック (Priority: P1)

開発者として、Pull Requestを作成した際に、コードの品質チェック（型チェック・リンティング・ビルド）が自動的に実行され、結果がPR上で確認できるようにしたい。これにより、レビュー前に基本的な品質問題を検出し、チーム全体のコード品質を維持できる。

**Why this priority**: PRレビューの効率化が最も高い価値を持つ。手動での品質チェック漏れを防ぎ、マージ前に問題を検出することが最優先。

**Independent Test**: Pull Requestを作成し、自動的にワークフローが起動され、成功/失敗の結果がPR上に表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** mainブランチに対するPull Requestを作成した状態で、**When** ワークフローが実行される、**Then** 型チェック・リンティング・ビルドが順に実行され、すべて成功した場合にPR上に成功ステータスが表示される
2. **Given** 型エラーを含むコードでPull Requestを作成した状態で、**When** ワークフローが実行される、**Then** 型チェックステップが失敗し、PR上に失敗ステータスとエラー内容が表示される
3. **Given** リンティングエラーを含むコードでPull Requestを作成した状態で、**When** ワークフローが実行される、**Then** リンティングステップが失敗し、PR上に失敗ステータスが表示される

---

### User Story 2 - mainブランチへのPush時の自動ビルド検証 (Priority: P2)

開発者として、mainブランチにコードがマージ（Push）された際に、ビルドが正常に完了することを自動的に検証したい。これにより、mainブランチが常にビルド可能な状態であることを保証できる。

**Why this priority**: mainブランチの健全性維持は重要だが、PR時のチェックがあれば多くの問題は事前に検出されるため、P1に次ぐ優先度とする。

**Independent Test**: mainブランチにPushし、自動的にワークフローが起動されてビルドが成功することを確認する。

**Acceptance Scenarios**:

1. **Given** mainブランチにPushが行われた状態で、**When** ワークフローが実行される、**Then** 型チェック・リンティング・ビルドが実行され、結果がコミットステータスとして表示される
2. **Given** mainブランチへのPush後にビルドが失敗した状態で、**When** 開発者がリポジトリを確認する、**Then** 失敗したワークフロー実行の詳細ログが確認できる

---

### Edge Cases

- ワークフロー実行中にPull Requestが更新（新しいコミットがPush）された場合、古い実行がキャンセルされ新しい実行が開始されること
- mainブランチ以外のブランチへのPush時にはワークフローが実行されないこと
- 依存パッケージのインストールが失敗した場合、適切なエラーメッセージが表示されること

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: mainブランチへのPush時に、型チェック・リンティング・ビルドを含む品質チェックワークフローが自動的に実行されなければならない
- **FR-002**: mainブランチに対するPull Request作成・更新時に、同じ品質チェックワークフローが自動的に実行されなければならない
- **FR-003**: ワークフローは型チェック、リンティング、ビルドの各ステップを含み、いずれかが失敗した場合にワークフロー全体が失敗として報告されなければならない
- **FR-004**: ワークフロー実行結果はPull Request上またはコミットステータスとして表示されなければならない
- **FR-005**: 同一Pull Requestに対して新しいコミットがPushされた場合、進行中の古いワークフロー実行がキャンセルされなければならない
- **FR-006**: 依存パッケージはキャッシュされ、ワークフロー実行時間の短縮に活用されなければならない

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: mainブランチへのPush、またはmainに対するPull Request作成時に、ワークフローが100%の確率で自動起動すること
- **SC-002**: ワークフロー全体の実行が5分以内に完了すること
- **SC-003**: 型エラー・リンティングエラー・ビルドエラーの100%がワークフローで検出されること
- **SC-004**: 同一PRへの連続Push時に、古いワークフロー実行が自動キャンセルされること

## Assumptions

- GitHubリポジトリが既にセットアップされており、GitHub Actionsが有効化されている
- プロジェクトの品質チェックコマンド（型チェック、リンティング、ビルド）は既に定義されている
- ワークフローはパブリックリポジトリまたはGitHub Actions利用可能なプライベートリポジトリで実行される
- テストフレームワーク（Vitest等）は現時点では未導入のため、ワークフローのテストステップはビルド（型チェック含む）とリンティングに限定する
- Storybook のビルドはCIワークフローの対象外とする（将来的に追加可能）
